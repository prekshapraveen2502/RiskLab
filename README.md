# RiskLab

A portfolio risk pipeline that computes Value at Risk and Expected Shortfall, then tests whether those numbers actually hold up out of sample. On top of the numbers sits an AI layer: a language model can answer questions about the results, but it can only read figures the deterministic engine already computed — it never does the arithmetic itself.

Computing a VaR number is a one-line quantile. The harder question is whether the number is trustworthy, which is what most of this project is about: rolling out-of-sample forecasts with no lookahead bias, breach detection, and a Kupiec unconditional coverage test with a real p-value.

---

## Results

Five-ETF portfolio, 2018-01-02 to 2026-08-31, 2,176 daily returns.

| Metric | Value |
|---|---|
| Historical VaR (95%) | **1.1643%** |
| Expected Shortfall (95%) | **1.7895%** |
| Evaluated out-of-sample forecasts | 1,926 |
| Breaches observed | 105 |
| Observed breach rate | **5.4517%** |
| Expected breach rate | 5.0000% |
| Kupiec LR statistic | 0.804760 |
| Kupiec p-value | **0.369674** |
| Reject null at 5% | **No** |

The breach frequency is statistically consistent with 95% coverage. That means unconditional coverage was not rejected — it is not evidence that the model is correct. See [Limitations](#limitations).

Figures come from `data/processed/risk_summary.json`, regenerated by `run_pipeline.py`.

## Architecture

```
config/portfolio.csv
        │
        ▼
  ingestion ──────── MarketDataProvider protocol (yfinance adapter)
        │
        ▼
  validation ─────── portfolio weights + market data quality gates
        │
        ▼
  returns ────────── prices → asset returns → weighted portfolio return
        │
        ▼
  risk ───────────── Historical VaR · Expected Shortfall · 250-day rolling VaR
        │
        ▼
  backtest ───────── breach detection → summary → Kupiec coverage test
        │
        ▼
  persistence ────── 5 Parquet files + risk_summary.json
        │
        ▼
  AI layer ───────── 5 read-only tools over the persisted outputs
```

**Ingestion** pulls daily adjusted close prices behind a one-method `typing.Protocol`, so the rest of the pipeline never knows where prices came from. **Validation** checks the portfolio (required columns, missing values, duplicate tickers, negative weights, weights summing to 1.0) and the price data (empty frame, missing tickers, duplicate dates, non-chronological index, non-positive prices, missing-value threshold). **Returns** converts prices to simple daily returns and weights them into one portfolio series, aligned by ticker name rather than column position. **Risk** computes full-sample VaR and ES plus a 250-day rolling VaR. **Backtest** flags breaches, summarises them, and runs the Kupiec test. **Persistence** writes five Parquet files and a JSON summary.

Orchestration is a single function, `run_analysis()` in `run_pipeline.py`. Each stage is a pure function, so the pipeline is a straight line with no hidden state.

## AI layer design

The agent answers questions about the risk results. It cannot compute anything.

- **Five read-only tools**, registered in `TOOL_REGISTRY` (`src/ai/tools.py`): `get_portfolio_risk_overview`, `get_model_validation_results`, `get_var_breach_details`, `get_worst_portfolio_days`, `get_period_risk_snapshot`. Each reads the persisted Parquet and JSON files and returns a plain dict. None has a write path.
- **Allowlisted dispatch.** `execute_tool()` rejects any unregistered tool name and any unexpected argument. There is no way for the model to reach code that was not explicitly exposed.
- **Multi-step loop with a step cap.** `run_validation_agent()` sends the question plus the tool schemas, executes whatever tools the model asks for, feeds the results back, and repeats until the model returns text or hits six steps, at which point it raises rather than looping.
- **All maths stays outside the model.** The system prompt instructs the model to read every number from a tool result and never recompute a statistic. A grounding check (`src/ai/grounding.py`) then verifies this automatically after every run: it extracts each number from the answer and confirms it traces to a value that run's tools actually returned.
- **Every tool call is logged.** The result carries an ordered trace of each call with its arguments, plus the full tool output, which is what the saved transcripts contain.
- **Two provider adapters** behind one Protocol: OpenAI (Responses API) and Gemini (google-genai). The agent loop does not know which is in use.

### Live sample runs

The agent has been **run live against OpenAI `gpt-4.1-mini`** on three questions. Full transcripts — provider, model, command, question, every tool call with arguments, complete tool results, and the model's final answer — are in [`docs/sample_runs/`](docs/sample_runs/):

| Run | Question | Tools the model chose | Steps |
|---|---|---|---|
| [01](docs/sample_runs/01-backtest-and-kupiec.md) | Summarize the backtest results and whether the VaR model passes the Kupiec test. | `get_portfolio_risk_overview`, `get_model_validation_results` | 3 |
| [02](docs/sample_runs/02-worst-breach-days.md) | What were the five worst breach days, and how large were they compared with the VaR forecast? | `get_var_breach_details(limit=5)` | 2 |
| [03](docs/sample_runs/03-breach-clustering.md) | Is there any sign that breaches cluster together? | `get_var_breach_details(limit=100)` | 2 |

Tool choice was not steered: the model picked `limit=5` for the "five worst" question and `limit=100` for the clustering question on its own.

**Grounding check: 35 numeric claims across the three answers, 0 ungrounded.** 24 were strongly grounded and 11 fell in the weak bucket (zero decimal places or fewer than two significant figures, so they match too easily to count as strong evidence). Every quoted date was present in that run's tool output. The figures were also checked by hand against the tool results for the most number-dense answer.

`data/processed/ai_validation_report.json` and `.md` are the agent's own output from **run 03** (the clustering question), left in place by the last live run. They are real model output, not the deterministic fallback described below.

### Grounding check

`audit_grounding()` runs after every agent run (disable with `--no-check-grounding`). For each number in the answer it searches that run's tool output for a supporting value, where a claim stated to *d* decimal places admits half a unit in the last place:

| Match kind | Rule |
|---|---|
| `direct` | the tool returned the value as stated |
| `percent` | the model wrote a decimal as a percentage |
| `complement` | a confidence level read from a significance level, **only** for fields whose name contains "significance" or "confidence" |
| `absolute_value` | magnitudes agree but signs differ, recorded as such |

Each claim records how it matched and how many distinct evidence values it matched — more than one means the claim is ambiguous. Claims with no decimals or fewer than two significant figures are reported in a separate **weak** bucket rather than counted as strongly grounded. Dates, and list ordinals at the start of a line, are masked before extraction and counted in the output, so anything the check declines to inspect is visible rather than silently dropped.

The check only ever reports. It never edits the model's answer.

**The Gemini adapter has only been tested with mocked SDK responses.** No request has been sent to a Gemini endpoint, and `gemini-3.7-flash` is an unverified configuration value.

## How to run it

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt

python run_pipeline.py             # fetch data, compute risk, backtest, persist
python -m pytest -q                # 279 tests, no network required
```

Requires Python 3.11+ (developed on 3.14).

### The validation agent

```bash
export OPENAI_API_KEY=...                  # OpenAI
export GEMINI_API_KEY=...                  # Gemini

RISKLAB_LLM_PROVIDER=openai \
RISKLAB_LLM_MODEL=gpt-4.1-mini \
python run_validation_agent.py --verbose --question "Is there any sign that breaches cluster together?"
```

| Variable | Purpose | Default |
|---|---|---|
| `RISKLAB_LLM_PROVIDER` | `openai` or `gemini` | `gemini` |
| `RISKLAB_LLM_MODEL` | overrides the adapter's default model | `gpt-4.1-mini` / `gemini-3.7-flash` |
| `OPENAI_API_KEY` | credential for the OpenAI adapter | — |
| `GEMINI_API_KEY` | credential for the Gemini adapter | — |

`--question` is optional; without it the agent is asked the standard model-validation question. Credentials are read only from the environment and are never written to the repository or printed.

**Without any API key** the entry point makes no LLM call. It warns, then prints and saves a deterministic validation report built directly from `risk_summary.json` (`data/processed/deterministic_validation_report.txt`), with the same Kupiec interpretation and limitations the agent is instructed to follow. That file is clearly distinct from the agent's own `ai_validation_report.*`.

## Testing

279 tests, no network calls anywhere in the suite.

| Area | Tests |
|---|---|
| Backtesting and Kupiec | 37 |
| AI tools and agent loop | 74 |
| Historical VaR / ES | 21 |
| Pipeline orchestration | 18 |
| Provider adapters | 32 |
| Rolling VaR | 15 |
| Persistence round-trip | 15 |
| Returns and validation | 26 |
| Reporting | 10 |
| Grounding check | 31 |

Two tests carry most of the weight:

**No lookahead bias.** `test_rolling_var_has_no_lookahead_bias` perturbs one day's actual return to an extreme value and asserts that day's forecast does not move, while the next day's does. The second half matters — without it, an implementation returning all-NaN would pass. A naive `.rolling(250).quantile()` includes the current day in its own forecast window, which silently invalidates the whole backtest; `calculate_rolling_historical_var` applies `shift(1)` first.

**Read-only guarantee.** Tests snapshot the size and modification time of all four persisted data files and assert both are unchanged after every tool is called and after a full agent run, so the AI layer provably cannot mutate the risk data.

The Kupiec implementation is tested against hand-computed values at known inputs rather than against its own output — at exactly the expected breach rate the LR statistic must be 0 and p must be 1, and both are asserted. Degenerate cases (zero breaches, all breaches) are covered because the log-likelihood has a `log(0)` term that must be guarded.

Run with `python -m pytest`. The `-m` form is required because there is no packaging config placing the repository root on `sys.path`.

## Limitations

- **Kupiec tests breach frequency, not independence.** It would return the same verdict whether the 105 breaches were spread evenly or clustered in a single month. A Christoffersen independence test is the natural next addition and is **not built**. Run 03 shows the agent itself identifying the March 2020 cluster and recommending exactly this test.
- **The grounding check is string matching, not verification.** It confirms that a number appears in the tool output; it cannot catch a correctly sourced figure used to support a wrong claim, a right value attached to the wrong date, or a false statement containing no numbers. Where a claim matches several evidence values the reported source may be a coincidence — in run 02 the model's "5.0%" is attributed to `returned: 5` rather than the breach magnitude it meant, which is what the distinct-match count is there to expose.
- **Weak claims are not strongly verified.** 11 of the 35 claims in the sample runs are low precision (for example "105 breaches" or "5%"), so they match within half a unit of more than one plausible value.
- **Only the OpenAI adapter has run live.** The Gemini adapter is tested with mocks only, and its default model name is unverified against a real endpoint.
- **Historical VaR assumes the sample represents the future** and cannot anticipate a shock without precedent in the data.
- **Expected Shortfall is estimated from a thin tail** — roughly 109 observations at 95% — so it is less stable than the VaR estimate.
- **Single-machine and in-memory.** Every run recomputes the full history; there is no incremental or partitioned processing.
- **Analysis dates and the rolling window are constants** in `run_pipeline.py`, not CLI arguments.
- **No data versioning.** Outputs are overwritten in place, so a vendor revising historical prices leaves no trace.
- **A tool error aborts the whole agent run** rather than returning the error to the model for a retry.
